## 0. 一句话结论

**要换的不是数据库，是「查询在哪儿执行」。**

两个 codex session 的完整命令记录（§0.1 / §0.2）量出四件事，按证据强度排：

1. **链路层完全没被服务。** 158 次带目标的工具调用里，`page:` 118 次、`comp:` **1 次**；
   157 次相邻跃迁里 108 次是 `page → page`。77 个不同页面的**广度普查**，几乎零下钻。
   这是「业务链路」需求被拆成 77 次单点查询、由人脑拼接的形态（§0.2）。
2. **节点层有定位但不交回属性。** 215 条直接 jq 打在原始文件上，平均**每个普查过的
   页面补读 2.8 条 jq**；`--explain 'comp:…'` 全程只用了 1 次——用了也拿不到想要的字段。
3. **五个高频字段根本没抽进图**（`businessDesc` / `notNull` / `validMessage` /
   `resourceRoot` / `modelDataType`，全仓 `grep src/` 命中为 0）。任何后端都读不到
   一个不存在的事实（§0.1.1）。
4. **32% 的 jq 压根不是查询**，是在裁剪工具自己的输出（§0.1）。属输出契约。

链路层要有界多跳、节点层要扁平表——**两层都要，而两层今天都被同一个架构约束卡住：
查询在客户端内存里执行，所以必须先全量 hydrate，所以冷启动 1,008 秒，所以没人敢做
跨 77 页的链路查询。** 换 redb 为别的库不解决这个；把查询下推到存储里执行才解决。

> **本文第 1 / 2 版的错误更正**：第 2 版据「315 条 jq 里只有 4 条图形状」推出
> 「图需求只有 1.3%」。该推断作废——jq 按文件工作，跨文件链路结构上装不进 jq 语料；
> 工具也没有链路动词，同样装不进工具语料。两条通道都堵死时，未满足的链路需求表现
> 为**重复**而非查询。详见 §0.1.1b 与 §0.2。

### 0.1.1b 方法论盲区：这份统计**不能**用来推断图需求的大小

> 2026-09-05 二次修订。上一版把「315 条里只有 4 条图形状」直接读成「图需求只有
> 1.3%」。这个推断是错的，原因有两层，两层都是构造性的：
>
> 1. **jq 按文件工作。** 跨 `.spg` 的链路在 jq 里根本无法表达，因此它**不可能**出现
>    在 jq 语料里。用 jq 语料去测跨文件图需求，等于用渔网量空气。
> 2. **工具没有链路动词。** 见 §0.2——`--relations` / `--explain` 都是**单目标**的。
>    链路需求也无法出现在工具调用语料里。
>
> 两条通道都堵死时，未满足的链路需求不会表现为「一条查询」，而会表现为
> **重复**：把同一个问题拆成几十次单点查询，然后由人在脑子里拼。§0.2 量到的
> 正是这个形态。
>
> 因此 §0.1 的表**只是「jq 被用来干什么」的分类**，它准确回答了「A 桶是不是查询
> 问题」和「哪些字段没抽」，但**不回答**「图需求有多大」。后者见 §0.2。

### 0.1.2 对计划的三条修正

> ⚠️ 下面第 2、3 条已被 **§0.2.2 修订/作废**，保留原文只为留痕。第 1 条仍成立。

1. **A 桶（32%）根本不是查询问题。** 分析者拿到工具输出后手工重投影，保留
   `query_target` + `summary` 的若干子键 + `details` 的若干子键。这是「给多了 / 给的
   切片不对」，属输出契约（`--budget` 档位、字段选择、profile），**在 `output.rs` 里
   解决，一行后端代码都不用改**。
2. **想要的形状是表，不是图。** 46% 显式 `@tsv`，33% 跨文件。这直接**反对**计划
   §4 把「Grafeo 原生 Cypher」定为首选路线——需求形状更接近
   `SELECT comp_id, action_type, data_set, condition_exp FROM actions WHERE page = ?`。
   若最终真要选后端，这条证据把天平推向关系型投影而非 Cypher。
3. **1.3% 才是图查询。** 315 条里 4 条。以此为据启动一次图数据库迁移，投入产出比
   是失衡的。

### 0.1.3 一个被忽略的张力

填 §0.1.1 的覆盖缺口意味着**往图里抽更多字段**，图会变大，而冷启动已经是
**1,008 秒**（89,094 节点 / 199,575 边 / 514 MiB，`performance-baseline.md:775-790`）。
覆盖与冷启动相互拉扯：不解决「查询在存储里执行还是在内存图里执行」，补覆盖只会让
冷启动更糟。这两件事必须一起决策，但**它们都不是「选哪个数据库」**。

## 0.2 补充证据（二）：468 条工具调用——未满足的链路需求长什么样

同两个 session，另有 468 条 `metadata-checker` 调用，去重 248 条，其中 158 条带明确
目标。这才是测「图需求」的正确样本。

**动词与目标分布：**

| 动词 | 次数 | 目标类型 |
|---|---:|---|
| `--find <业务名>` | 32 | 裸名（`合同解约`、`订单提交`、`线索总览`…）——找入口 |
| `--relations 'page:…'` | 76 | 页面 |
| `--explain 'page:…'` | 31 | 页面 |
| `--query-page-logic 'page:…'` | 11 | 页面 |
| `--relations 'model:…'` | 5 | 模型 |
| **`--explain 'comp:…'`** | **1** | **组件——整个会话只有 1 次** |

**目标类型统计：`page:` 118 次 / `comp:` 1 次 / `model:` 5 次。**

**相邻调用的跃迁：157 次相邻中 108 次是 `page → page`**，`page → comp` 仅 1 次，
`page → model` 仅 1 次。

**深度：77 个不同页面被查了 118 次，只有 19 个页面被查过 1 次以上；同页面连续深挖
的串只有 2 段，最长 3 次。**

### 0.2.1 这组数字说明了什么

分析者的实际动作是：

```
--find '合同解约'                    找到入口
  → --relations 'page:A'            A 页的报告
  → jq A.spg                        A 页内部细节（平均每页 2.8 条 jq）
  → --relations 'page:B'            B 页的报告
  → jq B.spg
  → …重复 77 个页面…
  → 在脑子里把 A→B→C 的链路拼起来
```

**77 个页面的广度普查，几乎零深度下钻，跨类跃迁只有 2 次。** 这不是「分析者不需要
链路」——恰恰相反，这是**链路需求被拆成了 77 次单点查询**的样子。工具能回答
「这一页有什么」，回答不了「这条业务链路经过哪些页、在哪一步写进哪张表、哪个条件
把它挡住」，于是人只能一页一页扫完自己拼。

「首先要看到链路，然后再深挖节点」这句话，在数据上的投影是：

- **链路层**：工具无对应动词 → 表现为 77 次页面普查（而不是 0 次链路查询）；
- **节点层**：工具有定位但不交回属性 → 表现为 215 条 jq（`comp:` 动词全程只用 1 次，
  因为用了也拿不到想要的字段）。

**两层都没被服务，而且失败形态完全不同：链路层的失败表现为重复，节点层的失败表现
为出走。** 我上一版只看见了后者。

### 0.2.2 对 §0.1 结论的修正

`§0.1` 的三条修正里，第 2、3 条要改：

- **第 3 条「1.3% 才是图查询」作废。** 它测的是 jq 语料，而 jq 结构上装不下跨文件
  链路。正确的读法是：**图需求的证据在 §0.2 的 77 页普查里，不在 jq 里。**
- **第 2 条「想要的形状是表不是图」要收窄**为：**节点层**想要的形状是表（46% `@tsv`、
  33% 跨文件，这个证据仍然成立）；**链路层**想要的是有界多跳遍历。两层都要，不是
  二选一。原来据此反对 Cypher 的力度要降低——反对的是「只有 Cypher」，不是「要
  Cypher」。

§0.1 的第 1 条（A 桶 32% 是输出契约问题）和 §0.1.1（五个字段没抽进图）不受影响，
那两条是直接观测，不依赖推断。

## 0.3 承重结论：内存持久化是所有问题的公共约束

基线里最硬的事实是 **stdio 启动加载 1,008 秒**（89,094 节点 / 199,575 边 / 514 MiB，
`performance-baseline.md:775-790`）。这不是 redb 慢，是「启动即把整张图 hydrate 进
内存、查询在内存里跑」这个架构决定的。

把 §0.1 / §0.2 摆在一起看，它不是一个并列问题，是**其余问题的公共上游**：

| 问题 | 证据 | 为什么卡在内存架构上 |
|---|---|---|
| 链路层无动词 | 118 次 `page:` / 1 次 `comp:`；77 页广度普查 | 跨 77 页的多跳要在内存图上做 → 必须先全量 hydrate → 没人敢跑 |
| 节点层不交回属性 | 215 条 jq，每页均 2.8 条 | 交回全属性意味着往图里塞更多字段 → 图更大 → hydrate 更慢 |
| 五个字段没抽 | 全仓 `grep src/` = 0 | 同上，扩覆盖与冷启动直接对冲（§0.1.3） |
| 输出给多了 | 100/315 条在裁剪输出 | 唯一**不**受此约束的一条，纯 `output.rs` |
| 冷启动 1,008 s | 基线实测 | 就是它本身 |

**所以「一次落库，之后做成熟的本地查询」这个方向是对的，而且它是前置而非收尾。**
只要查询还在内存图里执行，扩覆盖会让冷启动更糟、链路查询贵到不可用——三件事互相
锁死。查询一旦下推到存储里执行，三把锁同时开：链路多跳按需读、属性按需取、启动不
再 hydrate。

### 0.3.1 这件事的真正难点不是选库，是抽象

`GraphReadStore` 今天的方法集是 `get_node` / `get_node_edges` / `iter_nodes` /
`node_count` / `edge_count`（`src/graph_store.rs:122-134`）。**这个接口本身强制遍历
发生在调用方**——多跳只能在客户端逐跳 `get_node_edges`，每跳一次往返；要快就只能
先 hydrate。

也就是说：**换库不换抽象，等于把同一个瓶颈换个地方复现。** 真正的改造是给
`GraphReadStore` 加一层可下推的能力（过滤、投影、有界多跳、聚合），让实现方决定在
哪儿执行。redb 之上能不能做出可接受的下推，本身就是一个该先做的 spike——而且它比
迁移便宜得多，**做完才知道到底要不要换库**。

这也顺带回答了 §2.4 的 wasm 问题：抽象保住了，native 侧走下推实现，wasm 侧走现有
遍历实现，两边共用同一套查询语义。

## 1. 该保留的（不要在后续修订里丢掉）

1. **「没有真实样例，不进入后端选型结论」这道门槛**（阶段 0）。这是全篇最值钱的一句。
   图数据库选型最常见的失败模式就是先爱上一个引擎再去找需求。
2. **两个平面的切分**：图查询返回结构化关系 + 文件定位，原始 JSON 由既有文件读取
   链路提供。拒绝把 raw body 复制进候选后端是对的——那等于用图数据库重新实现一个
   很差的文档库，而项目已经有能直接读 `.spg`/`.tbl` 的链路。
3. **阶段 4 的不侵入原型 + 那条可证伪的检查**：「查询-only 进程必须验证不打开、不
   hydrate redb，不能从已 hydrate 的 redb 再生成投影」。这条把「看起来变快了」和
   「真的绕开了 hydrate」区分开，是全篇最硬的验收设计。
4. **阶段 6 拒绝把 M58.3 遗留算作已解决**。迁移项目最典型的死法就是把旧身份问题
   原样复制到新后端。

## 2. 该改的

### 2.1 主假设错位：把「绕开全量 hydrate」提为头号指标

现状：`89,094` 节点 / `199,575` 边 / graphdb `514 MiB`，stdio 启动加载
**1,008.1 s / 1,011.8 s**（2 轮实测，`performance-baseline.md:775-790`）。

这个数字的成因是启动时把整张图 hydrate 进内存，不是 redb 的 KV 读写慢。因此：

- 若新后端仍然「启动即 hydrate、查询在内存图里跑」，换 redb 为 DuckDB/Grafeo
  **不会改善这 1,008 秒**，只会换一种编码格式；
- 若查询下推到存储引擎里执行（按需读，不 hydrate），那么**redb 也未必需要换**——
  需要换的是 `GraphReadStore` 之上的查询执行模型。

**建议**：阶段 5 的头条指标改为「冷启动 → 首条查询返回」的端到端 wall time，
数据库体积降为次要指标（计划第 5 节已经说「决策不能只看数据库大小」，但阶段 5 的
指标清单仍把体积排在延迟前面）。同时在阶段 2 给每个候选加一列显式表态：
**该候选是否支持查询下推、下推到什么粒度**。

### 2.2 F4 / PR4a 的排序反了：迁移机制目前根本不存在

计划阶段 6 写「须先重新处理 M58.3 尚未完成的页面局部身份/schema 与重建验收，
**或**明确记录兼容适配器」。这个「或」是个陷阱：

- 适配器保住全局 `model:<name>` 身份，等于把缺陷平移进新后端；
- 而按 M58.3 spec 的迁移矩阵（`:191-230`），改身份要动**每一类边的端点**：
  `Contains`(model→field)、`Reads`/`FieldWrite`、`FieldAlias`、
  `DataflowInput`/`DataflowOutput`、`DependsOn`(cond→owner)、
  `DependsOn`(cond→符号)，外加 `next_queries` 的 **57 处调用 / 16 个文件**审计。

**这套迁移做两遍（一遍在 redb 上、一遍在新后端上）严格劣于做一遍。**

更要紧的是一条**已核实的事实**：schema 版本强制重建机制**没有实现**。全仓
`grep graph_schema_version` / `GRAPH_SCHEMA_STALE` 只命中
`src/diagnostics.rs:39` 的一句「PR4a 的 GRAPH_SCHEMA_STALE 待该 PR 再引入」。
而 spec 已写明：bump `REDB_V2_SCHEMA_VERSION` **不会**重建旧 v1 节点——版本不匹配
只是 `read_v2_layout` 返回 `None` 回退 v1，`--build-graph` 又按文件 hash 跳过未变
文件。

结论：**今天这个仓库没有任何能强制全量重建的开关。** 任何 schema 变更——换后端也
好、F4 局部身份也好——都会撞上「旧库静默按旧口径继续服务」。

**建议**：把 **PR4a（`graph_schema_version` 权威键 + hydrate 前校验 + fail-closed
`GRAPH_SCHEMA_STALE` + 强制全量重建路径）提为阶段 4 的前置**，而不是留在 deferred
里。它不依赖任何后端选型结论，成本远小于迁移本身，且**无论最终换不换后端都必须有**。
阶段 4 的原型投影 schema 应当直接按 **F4 之后**的局部身份文法生成，即使此时 redb
运行时仍跑旧身份——否则原型验证的是一个已知要废弃的 schema。

### 2.3 二进制体积应当是阶段 2 的淘汰规则，不是打分项

约束：release binary ≤ 10 MB（AGENTS.md），计划记录当前约 3.6 MiB。

计划把「二进制体积」列为研究维度之一，与「维护状态」「许可证」平级打分。但这不是
打分项，是**硬淘汰线**：静态链接的 DuckDB 体量是这个预算的数量级以上。

**建议**：阶段 2 开篇写死一条淘汰规则——任何候选把 release binary 推过 10 MB，
直接出局，不再投入 spike 成本。这很可能在花任何原型成本之前就淘汰掉 DuckDB，
从而把阶段 4 的两个 spike 缩成一个。（具体体积须实测确认，不要引用二手数字。）

### 2.4 缺一个硬约束：browser-wasm 目标

计划的研究维度写了「四平台」，指的是 `windows_amd64` / `macos_arm64` /
`linux_amd64` / `linux_arm64` 四个 native 平台。**`wasm32` 不在里面。**

但这个仓库是有 wasm 目标的：`Cargo.toml` 的 `browser-wasm` feature 独立成栈，
`redb` 只挂在 `cli-local` 下，`src/persistence/` 里 `redb.rs` 与 `indexeddb.rs`
并列，AGENTS.md 明写「browser-wasm 不得引入 redb」。

也就是说，今天的架构**已经**是「native 用 redb，wasm 用 IndexedDB stub，两边共用
`GraphReadStore` 抽象」。如果新后端编不到 wasm32，结果不是「换掉 redb」，而是
**多养一套查询引擎**——native 一套 Cypher/SQL，wasm 一套手写遍历。那比现状更差。

**建议**：阶段 2 增加一条硬维度「wasm32 可用性」，并明确表态：

- 若候选可编 wasm32 → 有机会统一两个平面；
- 若不可 → 候选只能定位为「native 侧的可选加速层」，`GraphReadStore` 抽象必须保留，
  且必须回答「wasm 侧的等价查询能力谁提供」。

这条不解决，阶段 6 会撞墙。

### 2.5 Grafeo 被指定为首选路线，但它的存在性/维护状态尚未验证

计划第 4 节把「Grafeo 原生 Cypher + `with_read_store`」定为阶段 4 的优先 spike，
而 Grafeo 的维护状态、许可证、Rust API 恰恰是**阶段 2 才要去核实**的内容。这是个
顺序倒置：先钦定了首选，再去做尽调。

我无法从本仓库或既有文档中确认 Grafeo 是一个真实、在维护的嵌入式 Rust Cypher crate；
计划里也没有版本号、仓库链接或日期。按计划自己的「证据规则」（优先官方文档和官方
仓库、记录版本日期、区分事实与未验证项），**Grafeo 目前属于未验证项，不该占据
「推荐初始技术路线」的位置**。

**建议**：阶段 2 完成前，第 4 节的推荐降级为「候选之一」；核实通过（有仓库、有
license、有近期 release、能编到目标平台）后再恢复首选地位。

### 2.6 基线臂：链路 + 表投影两层都要，且都必须可下推

四个候选里，第 3 个（基于现有 `GraphReadStore` 加一层查询）是**唯一完全不碰持久化
层**的方案：零迁移风险、零 schema 变更、零二进制膨胀、天然同时支持 native 和 wasm。
它应当是**基线（control）**，其余候选必须证明相对它有可测量的优势，才值得承担迁移
成本。

但证据说这层查询必须**同时**服务两种形状，不能二选一：

| 层 | 需求形状 | 证据 |
|---|---|---|
| **链路层** | 有界多跳遍历：从入口沿 `页→动作→模型→字段→页` 走 N 跳，带路径与每跳理由 | 77 页广度普查、108/157 次 `page→page` 跃迁（§0.2） |
| **节点层** | 关系型表投影：按事实类型摊平成行，跨文件过滤，`@tsv` | 46% `@tsv`、33% 跨文件、平均每页 2.8 条 jq（§0.1） |

> **修订**：本文第 2 版曾建议「`MATCH`/多跳留到确有需求再说——目前证据只有 4 条」。
> 该建议**撤销**，依据见 §0.1.1b：那 4 条测的是 jq 语料，装不下跨文件链路。链路是
> 一等需求，且按用户的表述是**先看链路再深挖节点**——链路层在使用顺序上还在前面。

**建议**：基线臂一版做两件事，共用同一套只读视图（`components`、`actions`、
`sources`、`conditions`、`writes`、`fields`、`pages`）：

1. **表投影**：`WHERE` 等值/前缀/正则 + 字段投影 + `LIMIT` + TSV/JSON 双输出；
2. **有界多跳**：给定起点、边类型白名单、最大跳数、最大结果数，返回路径 + 每跳的
   `source_file` / `json_path` / 理由。语法可以先不是 Cypher——`--trace <起点>
   --via ActionWrites,Reads --max-hops 4` 这种形态就能验证需求，语法糖以后再说。

关键约束（§0.3.1）：这两件事都必须能**下推到存储里执行**。做成客户端遍历就等于
默认全量 hydrate，那链路查询在 89k 节点上不可用，等于没做。

## 3. 该补的

1. **v2 shadow 的处置必须现在表态。** `src/graph_redb_v2.rs` 至今是 shadow-only
   （`REDB_V2_SCHEMA_VERSION = "m52-redb-v2-shadow"`，文件头注明「M53 再切入
   hydrate / incremental persist」），而 deferred 里又把「v2 shadow 族三处」「坏行
   hydrate 计数断言」列为**随 redb 退役**处理。这是最坏的中间态：既在付维护成本，
   又不交付收益。建议在阶段 5 决策门产出里显式二选一——**冻结**（明确不再投入，
   代码打上 deprecation 注释）或**落地**（切 hydrate/incremental persist）；在此
   之前不再新增 v2 代码。
2. **一个明确的「不换」出口。** 计划第 5 节第 8 条写「独立复核确认后，才决定是否
   移除或降级 redb」，但全篇没有描述「redb 留下」这个结局长什么样、需要补哪些工作。
   建议补一节「保留 redb 的收尾清单」（至少含 PR4a 强制重建、v2 处置、受限 Cypher
   查询层），让「不换」成为一个有交付物的结论，而不是「研究没做完」的默认状态。
3. **诊断计数基线需要在阶段 0 一并重新钉。** `performance-baseline.md` 记录
   `SCANNER_UNRECOGNIZED_CONTAINER_KEY = 312`（交叉验证口径 `moreFields 279 +
   params 33`）与 `SCANNER_DUPLICATE_COMPONENT_ID = 1,105`；复核返修 P1-7 改了组件
   身份判定，两个数都会漂移，312 的「精确吻合」交叉验证已不成立（见
   [2026-09-05 spec](../specs/2026-09-05-m58-3-condition-symbol-normalization-design.md)
   第 5 节）。阶段 0 既然要固定 `snapshot_id` 和内容 hash，顺带把这两个数重测回登，
   否则阶段 5 拿不到可比的前后对照。

## 4. 建议的执行顺序

**下推能力是主线，其余都挂在它下面。** 顺序按「先解锁公共约束，再填两层需求」排：

```
第 1 步     GraphReadStore 加下推接口（过滤/投影/有界多跳/聚合）
            ├── 这是 §0.3.1 的承重改造：换库不换抽象等于换个地方复现瓶颈
            ├── 先在 redb 上做实现 spike——做完才知道到底要不要换库
            └── 验收：89k 节点上跑一条 4 跳链路查询，不 hydrate 全图

第 2 步     链路动词（先于节点深挖，对齐"先看链路再深挖节点"）
            ├── --trace <起点> --via <边类型> --max-hops N --limit M
            ├── 返回路径 + 每跳 source_file / json_path / 理由
            └── 验收：77 页普查里至少 3 条真实业务链路，一条命令走完

第 3 步     表投影层（节点层）                                → 接住 B1/B3/B4/B5 207 条
            └── 只读视图 + WHERE + 投影 + LIMIT + TSV/JSON

并行 A      输出契约：--budget 之外补字段选择 / profile      → 接住 A 桶 100 条
            └── 唯一不受内存架构约束的一条，只动 output.rs，可随时插队做

并行 B      PR4a（schema 版本键 + fail-closed + 强制全量重建）
            ├── 不依赖任何选型结论，换不换后端都必须有
            └── 是 F4 与任何迁移的共同前置

第 4 步     scanner 覆盖：businessDesc / notNull / validMessage
            / resourceRoot(菜单树) / modelDataType
            └── 排在下推之后：下推没做之前扩覆盖会直接恶化冷启动（§0.1.3）

然后        阶段 0（缺口冻结，按 §0.1+§0.2 两条轴分类，不只按查询意图）
            + 诊断计数基线重测，同一个 snapshot_id 一次跑完

之后        只有在第 1 步的 redb 下推 spike 证明"redb 撑不住"时，才进阶段 2 尽调。
            先执行两条淘汰规则：
            ① release binary > 10 MB → 出局
            ② 不能编 wasm32 → 降级为 native 可选加速层，不得替换抽象
            并核实 Grafeo 的存在性与维护状态

再之后      F4 / PR4b（页面局部身份），schema 一次到位
            └── 阶段 4 原型的投影直接按 F4 后的身份文法生成

最后        阶段 4/5 原型与决策门，头条指标 = 冷启动到首条链路查询返回
```

核心主张不变但更锋利：**后端选型不是这条路的起点。第 1 步的 redb 下推 spike 才是，
而它同时也是判定"要不要换库"的那个实验。** 计划把这个实验放在阶段 4，前面压了三个
阶段的尽调——顺序应当反过来。
